# Assembly 设计宪章

基线：**Assembly Design Baseline 0.1.0**，2026-10-04。

适用于后续 Assembly package 的设计、实现和评审。它从当前 LEGO 实现、用户的功能语义要求及 [Assembly 设计与复用](https://lcnx4jkvmory.feishu.cn/wiki/QlLCwhO8wiDJRtkNGJQcJUIVnWf) 中抽象而来。跨领域契约是本次提出的设计基线；实际能力须由对应 package 验证。

## 宪章、思想、理念、规范分别负责什么

| 层次 | 职责 | 变化方式 |
|---|---|---|
| 设计宪章 | 固定目标、事实边界与应长期保留的不变量 | 有版本和原因的决策记录 |
| 设计思想 | 解释如何组织问题和方案，如功能优先、渐进抽象、分层访问 | 随使用证据修正方法 |
| 设计理念 | 在多个可行方案之间作取舍，如减少重复规划、保持可检查性 | 记录代价和取舍 |
| 设计规范 | 把原则变成对象、接口、状态、缓存和测试要求 | 按契约版本兼容演进 |
| 领域 profile | 填入机械、电路、仿真等领域的专用知识 | 由领域 package 维护 |

用词：**必须**表示本基线的不变量；**应**表示默认做法，偏离时记录原因；**可**表示可选能力。规范不能扩大用户授权，也不能覆盖宿主环境的执行权限。

## 目标

把过去已解决的局部工程问题保存为可复用方案。Agent 能理解其用途、确定适用条件、把它组合到新系统中，并取得与目标相称的验证证据。收益包括减少描述、检索、规划、编译和验证成本；实际零件、资源或动作数量仍按实例计数。

## C01：功能语义是主要检索入口

模块应明确说明用途、输入、输出、适用条件和限制。UID 只负责定位。检索先寻找能完成任务的候选，再用尺寸、接口、材料、协议、工况等条件筛选。检索分数不能证明最优性或可用性。

## C02：定义、实例和运行记录分离

定义保存复用方案；实例保存该方案在某个系统中的绑定、参数和环境；运行记录保存一次执行及其证据。必须能从结果追溯到准确的定义和依赖版本。同一发布身份/版本不得指向变化的内容。

## C03：Assembly 保存结构和可执行过程

结构描述组成与关系。过程说明如何产生、修改或安装它。必须声明支持的动作与执行范围。一个文件组合可以是有价值的结构模块，但若没有可执行过程，必须标明其复用方式为引用/复制/人工处理，而非程序重放。

## C04：模块边界允许渐进形成

首次构建可先保存完整历史。重复使用、局部修改或稳定功能出现后，再提取模块。已有清晰边界的子系统可直接定义。默认不要求自动发现边界，也不要求先建完整分类体系。

## C05：整体使用与按需下钻都应成立

原子对象和组合体都应作为可召回对象暴露。用户可整体使用，也可检查子模块和接口。原子边界由领域 profile 决定。上下文分页用于控制信息量，不自动产生新的工程模块。

## C06：组合必须通过显式接口和约束

接口类型、作用对象、单位、方向、允许值和兼容规则必须可查。名字相同或位置接近不能证明连接成立。跨领域连接需要显式适配器和假设；无法核实的条件保留为 unknown 或 unsupported。

## C07：原生工程数据与知识投影各有职责

必须指定权威源：原生文件、结构化定义或二者的受控组合。原始来源及未理解的字段应得到保留。摘要、向量索引和预览是投影，不能覆盖精确设计事实。知识库只是可替换的检索后端。

## C08：证据有对象、方法和适用范围

必须区分能力声明、验证计划和实际结果。验证记录应固定输入、检查器/求解器、配置、环境及结论范围。未知、未运行和不支持不能按通过处理。一个领域检查的通过不能自动升级为系统整体通过。

## C09：内部复用与实例环境验证分离

内部证据仅能在其前提仍成立时复用。每次组合必须判定新环境是否满足前提；环境未变时可命中环境缓存。外部载荷、供电、边界条件或依赖关系影响内部求解时，这些值也是内部计算的输入。

## C10：缓存必须覆盖因果依赖

缓存键必须包括会影响该结果的输入和工具配置。命中前检查完整性及适用性。不同阶段可以使用不同的依赖范围。只有领域适配器证明某些差异无关时，才能忽略它们。缓存不能提升验证等级。

## C11：执行状态和交付状态必须真实

构建应连续执行其必要阶段，并允许交付已经完成的独立产物。可选预览失败可降级；必要求解或验证失败必须反映在交付状态中。图形界面不可用时，继续可以独立完成的阶段，不把草稿称为已合格的制造/部署产物。

## C12：领域核心与宿主集成分离

工程对象和算法不应依赖 Pi、OV 或某个模型的内部实现。Pi package 提供工具入口和方法说明；领域适配器处理工程格式及求解。安装、setup、项目数据、会话资源和发布必须有清晰边界。多个 package 的名字和数据不能相互覆盖。

## 采用宪章时的默认取舍

- 优先保存可追溯事实；不为追求统一而丢掉领域语义。
- 优先选择可检查的小型领域适配器；共性经过至少两个实际领域验证后，再抽取共享代码。
- 优先减少重复规划和计算；不以“模块数越多”作为成果。
- 优先保留简单、明确的执行链；只有依赖关系允许时才增加并行或分布式执行。
- 优先显式 unknown；不让流畅的摘要、漂亮的预览或成功退出码替代工程验证。

## 演进

后续 package 在设计中声明采用的基线版本、适用规则和偏离记录。不能仅因为遵循这些文档就宣称“已通过认证”。当前基线没有认证机构或自动符合性引擎。

新的经验需要先对应具体失败或收益，再修改规则或领域 profile。兼容性变化要说明旧定义、缓存、证据和工程文件如何迁移。使用 [决策记录模板](../assets/DECISION.template.md) 保留理由。
