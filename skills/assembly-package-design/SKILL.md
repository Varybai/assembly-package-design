# Assembly package 设计

将已解决的工程局部问题，组织为可理解、可检索、可组合、可执行并可验证的版本化模块。沿用这里的通用决策，集中处理新领域的差异。

本 Skill 提供 **Assembly Design Baseline 0.1.0**。它是独立的设计先验和验收基线。各领域的工程文件处理、工具和求解器由后续 package 实现。文中的通用字段是设计建议，需要映射到目标领域的真实 schema。

## 使用方式

```text
/skill:assembly-package-design 为 KiCad 设计一个可安装到 Pi 的 Assembly package。复用稳压和传感器接口电路，保留原生工程文件，先给出领域契约、最小实现范围和验收用例，再完成已授权的实现。
```

用户只要求设计时，交付设计和必要模板；用户要求实现时，按范围继续实现、验证和打包。安装、提交或发布按用户已有授权执行。

## 按需读取

1. 新领域先读 [设计宪章](references/charter.md) 和 [领域适配](references/domain-adapters.md)。沿用宪章，用领域 profile 填充差异。
2. 定义数据、连接和文件所有权时读 [对象与文件契约](references/object-contract.md)。
3. 设计构建、验证、复用和缓存时读 [执行与证据](references/execution-evidence.md)。
4. 接入 Pi 或处理多包共存时读 [Pi package 规范](references/pi-package.md)。
5. 实现前选取 [验收规范](references/conformance.md) 中适用的用例，落实输入、预期结果和证据。
6. 参考外部 LEGO 实现迁移时读 [实现边界映射](references/implementation-map.md)。没有证据的能力保留为待实现。

不要为一个小改动读取所有参考。不要把全文注入每个运行任务；领域运行 Skill 只需要本领域的操作方法。

## 产出一个可实施的设计

在目标项目中使用 [设计模板](assets/PACKAGE-DESIGN.template.md)，记录这些决定：

- 用户要复用什么问题的解法；交付面向概念、仿真、制造还是实际运行。
- 本领域的原子对象、模块边界、接口、连接规则、参数和构建动作。
- 权威输入文件、依赖闭包、版本、生成文件，以及必须保留的未知字段。
- 检索与精确筛选的分工；模块整体召回和逐层展开的方式。
- 内部验证与实例环境验证的边界；哪些结果可以缓存，何时失效。
- 必要构建阶段、可选预览阶段、失败/取消后的可用产物和状态。
- Pi package 身份、工具前缀、项目数据目录、setup、迁移和发布范围。

将领域差异写进模板，不重新发明同 UID/版本不可变、证据有适用范围、实例隔离等通用规则。需要改变基线时，使用 [决策记录模板](assets/DECISION.template.md) 说明规则 ID、原因、影响、验证和迁移方式。设计取舍本身不构成额外审批要求。

## 从设计进入实现

先完成一个最小闭环：一个功能模块、至少两个不同环境中的实例、一项内部检查、一项环境检查、一份原生文件输出和可重复构建记录。再增加复杂模块和更多格式。

常见领域映射和首轮用例见 [跨领域例子](assets/DOMAIN-EXAMPLES.md)。这些例子是设计输入，不是经过实物验证的工程方案。

借鉴外部 LEGO 参照实现时先做差异检查：`.dat`、Z 向上、3×3 旋转、`place`、AABB、LeoCAD、Python/POSIX 和 `assembly_*` 都属于现有实现选择。新的领域可以使用不同表示和后端。源领域的数据文件不能仅改扩展名就变成新领域数据。

## 完成标准

设计交付要让下一位 Agent 能直接开始实施。实现交付还需有实际测试、可安装包、迁移路径和未实现能力清单。模块能生成文件、模拟通过、制造通过和现场运行通过是不同结论，分别报告。
